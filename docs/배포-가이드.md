# EveryDoing Windows 배포 가이드

이 문서는 EveryDoing의 **Windows 설치 파일을 직접 만들고 확인하는 절차**를 정리한다. 저장소는 Tauri 2와 NSIS 설치본을 사용한다. 0.3.0부터 앱에 업데이트 기능이 있어, 새 버전은 **서명 빌드 → GitHub Release 게시** 순서로 낸다(6장). 자동 빌드(GitHub Actions)는 아직 없다.

## 1. 준비

- Windows 10 또는 11과 Microsoft Edge WebView2 Runtime
- Rust 및 Cargo, Visual Studio Build Tools의 **C++ 데스크톱 개발** 구성 요소
- Tauri CLI 2 (`cargo tauri --version`으로 확인). 앱의 Tauri 본체가 2.12이므로 CLI도 2.12 이상을 쓴다
- GitHub CLI(`gh`) — 6장의 Release 게시에 사용
- 처음 빌드할 때 필요한 패키지를 내려받을 수 있는 네트워크 연결

Tauri CLI가 없다면 PowerShell에서 설치한다.

```powershell
cargo install tauri-cli --version "^2.12" --locked
cargo tauri --version
```

앱이 드라이브 루트를 MFT 방식으로 읽을 때 관리자 권한이 필요하다. 현재 `src-tauri/build.rs`는 Windows 빌드에 관리자 권한 요청 설정을 넣는다. 실제 설치본에서 UAC 요청과 스캔 동작을 확인한다. 빌드 명령 자체를 관리자 권한으로 실행할 필요는 없다.

## 2. 버전과 변경 사항 확인

PowerShell에서 저장소 루트로 이동한다.

```powershell
Set-Location 'D:\work\everydoing'
git status --short
```

다른 위치에 저장소가 있다면 `Set-Location` 경로를 그 위치로 바꾼다. 배포할 변경 사항과 미완성 파일을 확인한다. 새 버전을 배포할 때는 `src-tauri/tauri.conf.json`의 `version`과 `src-tauri/Cargo.toml`의 패키지 `version`을 같은 값으로 맞춘다. 사용자 앱은 이 버전 번호를 비교해 새 버전 여부를 판단하므로, 반드시 이전 Release보다 높여야 한다. 버전 변경 후 Cargo가 갱신한 `Cargo.lock`도 함께 확인한다.

## 3. 테스트와 설치본 빌드

저장소 루트에서 다음을 실행한다.

```powershell
Set-Location src-tauri
cargo test --locked
Set-Location ..
cargo tauri build --bundles nsis
```

테스트나 빌드가 실패하면 원인을 해결한 후 다시 진행한다. `--locked` 테스트에서 잠금 파일 갱신이 필요하다고 나오면 버전 및 의존성 변경을 확인하고 잠금 파일을 갱신한 뒤 다시 실행한다. Tauri 빌드가 끝나면 일반적으로 설치 파일은 다음 위치에 생성된다.

```text
src-tauri\target\release\bundle\nsis\EveryDoing_<버전>_x64-setup.exe
```

파일명과 CPU 아키텍처는 빌드 대상에 따라 달라질 수 있으므로 실제 빌드 출력과 폴더를 확인한다. 이전 빌드 파일이 남아 있을 수 있으니 생성 시각과 버전도 확인한다.

```powershell
Get-ChildItem 'src-tauri\target\release\bundle\nsis\*.exe' |
  Select-Object Name, Length, LastWriteTime
```

## 4. 설치본 확인

가능하면 별도의 테스트 PC 또는 테스트 사용자 계정에서 새 설치본으로 확인한다.

1. 설치와 실행이 되는지, UAC 관리자 권한 요청이 나오는지 확인한다.
2. 대상 폴더와 확장자를 설정하고 스캔한 뒤 수정일 기준으로 파일이 달력에 표시되는지 확인한다. 드라이브 루트 스캔과 일반 폴더 스캔을 각각 확인한다.
3. 검색, 파일·폴더 열기, 메모 저장, 재실행 후 데이터 유지, 재스캔과 진행 표시를 확인한다.
4. AI 요약을 사용할 경우에만 설정·동의 후 기능을 확인한다. 기본 설정에서는 외부 전송이 꺼져 있어야 한다.
5. 이전 버전이 설치된 환경에서는 업그레이드와 기존 설정·메모 유지 여부도 확인한다.

앱 데이터는 `%APPDATA%\EveryDoing\`에 저장된다. 이 폴더에는 개인 메모와 설정, 선택 기능에 사용되는 API 키가 포함될 수 있으므로 설치 파일이나 배포 자료에 포함하지 않는다.

## 5. 설치 파일 전달 또는 GitHub Releases 게시

개인적으로 사용할 때는 확인한 설치 파일을 대상 PC로 전달해 설치한다. 다른 사람에게 배포하려면 라이선스와 공개 범위를 먼저 확인한다. 현재 라이선스는 `LICENSE`에 명시되어 있다.

GitHub Releases를 사용할 경우의 수동 절차:

1. 배포할 소스가 원하는 커밋인지 확인하고 GitHub 저장소에 반영한다.
2. GitHub 저장소의 **Releases → Draft a new release**에서 버전에 맞는 태그를 선택하거나 만든다.
3. 변경 사항과 Windows 요구사항을 적고, 위에서 검증한 NSIS 설치 파일을 첨부한다.
4. 초안을 검토한 뒤 게시한다. 게시 전 파일을 교체했다면 교체한 파일로 다시 검증한다.

릴리스와 태그 생성은 외부에 변경을 반영하는 별도의 작업이다. 이 문서를 작성한 것만으로 실행되지는 않는다. Windows 코드 서명("PC 보호" 경고 제거)은 설정되어 있지 않다. 아래 6장의 업데이트 서명과는 다른 것이다.

## 6. 업데이트 배포 (0.3.0~)

앱은 "시작할 때 새 버전 확인"이 켜져 있으면 하루 한 번, 또는 설정의 "지금 확인"을 누르면 아래 주소의 `latest.json`을 읽는다.

```text
https://github.com/hanjjaem/everydoing/releases/latest/download/latest.json
```

`latest.json`의 버전이 앱 버전보다 높으면 사이드바에 "새 버전 · 업데이트" 버튼이 뜨고, 누르면 설치본을 내려받아 **서명을 검증한 뒤** 설치하고 앱을 다시 연다. 그래서 새 버전은 반드시 서명 빌드로 만든다.

### 서명 키

- 개인키: `%USERPROFILE%\.tauri\everydoing.key` (비밀번호로 암호화됨). **저장소에 넣지 않는다. 잃어버리면 이미 설치된 앱에 다시는 업데이트를 보낼 수 없다.** 따로 백업해 둔다.
- 공개키: `%USERPROFILE%\.tauri\everydoing.key.pub`. 같은 값이 `src-tauri/tauri.conf.json`의 `plugins.updater.pubkey`에 들어 있다. 키를 바꾸면 이 값도 바꿔야 하고, 바꾸기 전 버전의 앱은 새 키로 서명한 업데이트를 받지 못한다.

### 절차

1. 버전을 올리고(2장) 테스트를 통과시킨 뒤 커밋·푸시한다.
2. **서명 빌드** — 비밀번호가 화면과 명령 기록에 남지 않게 입력받는다.

   ```powershell
   Set-Location 'D:\work\everydoing\src-tauri'
   $env:TAURI_SIGNING_PRIVATE_KEY_PATH = "$env:USERPROFILE\.tauri\everydoing.key"
   $p = Read-Host "서명 키 비밀번호" -AsSecureString
   $env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($p))
   cargo tauri build
   Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD
   ```

   끝나면 `target\release\bundle\nsis\`에 `EveryDoing_<버전>_x64-setup.exe`와 `.exe.sig`가 생긴다.
3. **업데이트 정보 파일 만들기** — 저장소 루트에서:

   ```powershell
   node scripts/make-latest-json.mjs "이번 버전에서 바뀐 점 한두 줄"
   ```

4. **Release 게시** — 태그는 `v<버전>`. 설치본과 `latest.json`을 함께 올린다. 초안(draft)이나 사전 공개(prerelease)로 올리면 "latest" 주소에 잡히지 않아 사용자 앱이 새 버전을 보지 못한다.

   ```powershell
   $v = (Get-Content src-tauri\tauri.conf.json | ConvertFrom-Json).version
   $d = "src-tauri\target\release\bundle\nsis"
   gh release create "v$v" "$d\EveryDoing_${v}_x64-setup.exe" "$d\latest.json" --title "EveryDoing $v" --notes "바뀐 점"
   ```

5. **확인** — 이전 버전이 설치된 PC에서 설정 → "지금 확인"을 누르면 새 버전이 보이고, 사이드바 버튼으로 업데이트되는지 본다.

### 문제가 생겼을 때

- "Could not fetch a valid release JSON": Release가 없거나, `latest.json`이 첨부되지 않았거나, 초안·사전 공개 상태다.
- 서명 검증 실패: `latest.json`의 `signature`가 올린 설치본의 서명이 아니다. 3단계부터 다시 한다.
- 잘못된 버전을 냈을 때: 그 Release를 지우거나 사전 공개로 바꾸면 "latest"가 이전 Release로 돌아간다. 이미 업데이트한 사용자는 버전을 더 올린 수정본으로만 되돌릴 수 있다.

## 참고: 소개 페이지

`docs/index.html`은 앱 소개 페이지이고, 위에서 만든 NSIS 설치본과는 별도다. GitHub Pages 등으로 이 페이지를 공개하려면 저장소의 실제 호스팅 설정과 공개 범위를 확인해야 한다. 현재 이 문서는 페이지 호스팅이나 자동 게시가 설정되어 있다고 가정하지 않는다.
